### Authoring or modifying a skill

**You own the skill's voice.** This playbook contains the authoring procedure and requires no external skill.

1. Identify the requests that should trigger the skill, the result it produces, and its authorization boundary. Read the existing skill and nearby conventions before editing. Preserve its location and invocation policy unless the user requests a change. Use the [provider adapter](../../../providers/README.md) for personal skill paths and metadata. Project skills follow the repository’s conventions.
2. Write `SKILL.md` with YAML frontmatter enclosed by `---` lines. Require a lowercase kebab-case `name` and a nonempty `description` that states the intended requests and outcome. Keep the description a single YAML scalar, quoted or folded when punctuation or wrapping requires it. Keep operational instructions in the body. Preserve provider metadata and invocation policy rather than changing discovery behavior incidentally. Keep shared instructions independent of provider tool names and configuration paths.
3. Write only instructions that change a decision. State inputs, steps, success evidence, and failure handling. Link detailed references or reusable scripts from the entrypoint when they are needed. Resolve relative paths from the containing file. Keep skill dependencies inside Nanide skills and honor repository instructions and runbooks. Use current tool schemas rather than inventing tool names, arguments, permissions, or background execution guarantees.
4. Validate the saved artifact. Parse YAML frontmatter with an available YAML parser and check the required fields. Resolve local Markdown links and referenced files relative to each document, including linked anchors where used. Check referenced commands against the actual files and tool schemas. Confirm unchanged metadata and invocation policy stayed unchanged. Report any check that could not run rather than treating it as passed.
5. Exercise representative requests against the changed instructions. Include one intended trigger, one request outside the scope, and a failure or missing-tool case for operational changes. For authorization or lifecycle rules, check both allowed and prohibited transitions without performing unauthorized actions. Use independent read-only review for substantial changes. Tone-only edits need prose review and structural checks, not a benchmark suite. Fix contradictions and rerun affected checks.
6. Use [Opening a PR](opening-a-pr.md) when PR creation is authorized for the requested repository change. Personal skill edits need no repository PR. Review the complete diff and report the saved paths and validation evidence.

When in doubt, delete. Keep only prose that changes a decision. Explain a rule only when it is confusing without a reason. Match tone to scope. Point at structural sources such as types, READMEs, and config. Link bundled skills by path rather than restating them. Propose a new bundled skill only when no existing one fits a recurring workflow.

**Reply:** summary of the skill, key design decisions, validation notes.
